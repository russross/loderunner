Lode Runner port semantics
=========================

Status and boundaries
---------------------

Faithful emulation covers core level gameplay from active level start through the committed Died or LevelCleared snapshot: movement, digging, guards, gold, holes, exits, collisions, in-level scoring, sound, and gameplay timing. Ready screens, pause, session controls, transition tunes and bonuses, reloads, and level selection are application behavior outside that guarantee. High score tracking, display, persistence, qualification, and initials entry are absent. The Rust game retains death/restart, level advancement, pause, and sound/speed controls as session conveniences. It presents composed sprite shapes through local SDL texture updates and plays synthesized speaker edges. Input recordings replay idealized effective Apple II commands without expected state. Trace verification independently reexecutes those keys and compares state, events and model timing, while MAME boots original code and compares independently observed objects. Selected machine fixtures pass historically; this does not establish complete machine equivalence or cycle accuracy.

`sources/lode_runner_reveng/` vendors reference revision `113db1c16951717259c9ae5e128958b29de0634d`, including provenance and its CC BY-SA license. Root Cargo builds the `loderunner` application/library in `src/`, the observation library in `src/trace/`, and the MAME validation library in `src/mame/`. Gameplay files are flat in `src/`; keyboard and speaker interfaces live in `src/devices/`; integration tests live in `tests/`. Only the latest game implementation is retained.

Make drives incremental Cargo builds, producing `target/release/loderunner`. Checks run formatting, Clippy, then tests. `mostlyclean` removes compiler intermediates while preserving the release executable; `clean` removes Cargo outputs too. Neither removes source assets, traces or recordings.

Execution, storage, and initialization
--------------------------------------

The game executes native gameplay rules without interpreting 6502 instructions. Counters retain byte wrapping where gameplay depends on it; closed domains use enums. Score uses a bounded decimal value with modulo-100,000,000 addition and displays its lower seven digits.

Build.rs converts original 256-byte level sectors and executable sprite tables into native assets under Cargo OUT_DIR, tracking every input with rerun-if-changed. Runtime storage indexes complete generated sectors; sprites contain ten-bit rows, whole 110-bit masks and fixed setup-cost metadata. The reference remains authoritative and Cargo regenerates derived assets incrementally. There are no disk delays or controller emulation. Decoding visits rows top to bottom and columns left to right, consuming each low nibble before its high nibble. Tile values 10 through 15 become empty; only the first 224 bytes describe the 28 by 16 playfield.

Initialization visits rows bottom to top and columns right to left. The first encountered player survives; other player markers disappear. Guards receive slots 1 through 5 in the same traversal; extras disappear. At most 45 hidden ladders are retained in allocation order and removed from both logical maps. Accepted actor markers occupy the active map only. Gold remains in both maps until collection. The game composes Foreground and Background shapes in the same order, followed by status text. No player is an initialization error. Initial rendering costs are outside the initial virtual-clock origin.

The native session decodes and validates every sector once into a Level before SDL opens. Initial load and reload use those validated boards. Configuration embeds all level sectors, starting index, and ready-wait policy; original configuration contains 150 boards. Reload retains gameplay time, speaker history, sound preferences, score, guard scheduler phase, resurrection column, facing flags, falling pitch, and the pending landing-sound flag. It increments global attempt identity and resets board-local state and exit availability. Lives are unlimited. A separate u32 lives_used counter begins at one, increases after each death/restart, and resets to one on level changes. The status strip labels this counter USED and displays its lower three digits. Supported movement consumes pending landing sound and resets falling pitch to $20; loading alone does neither. Death presentation advances falling pitch once when a landing sound remains pending.

Devices and graphics
--------------------

Game owns a composed Scene and a Display that retains the selected Foreground/Background Layer, scene-refresh flags, and the simple RGB cache. Scene supplies visible ink and player-contact data. The SDL host owns Presentation, which defaults to the sibling `../crt` library pipeline and can select the simple decoder. Gameplay has no HIRES addresses, page buffers, soft switches or display-hole storage; the presentation adapter serializes scene ink at the output boundary.

The build decodes each supported sprite into a whole shape. Runtime composition uses overlay, erase and replacement rules corresponding to the original masked writes and `(foreground XOR background) AND shifted_sprite` contact. All supported writes share the high color-phase bit. The CRT adapter packs each visible row into forty seven-data-bit HGR bytes with bit seven set, preserving that blue/orange phase, and uses AppleProfile::IieNtscV1 at eight samples per carrier. Color, horizontal electrical filtering and local vertical beam overlap are supplied by `crt`. The selectable simple digital decoder preserves its original adjacent-white and parity-based artifact-color rules.

Only player redraw evaluates shape contact; guard-entry and hole-closure contact use logical occupancy independently. Sprite erasure can remove another actor's overlapping pixels, and background pixels suppress foreground overlap. Current poses alone therefore do not describe every contact-relevant state. Game owns a Scene whose ten-by-eleven local cells each retain a 110-bit background mask and a 110-bit foreground/background difference mask. Appearance operations update these masks through whole-shape Boolean rules; player contact intersects its translated animation shape with at most four nearby cells. Erasure restores background across its enclosing fourteen/twenty-one-pixel span, not just its silhouette. The scene includes status placement and visible right-edge spill. RGB presentation reads these masks without changing contact state. `sources/analysis/COLLISION.md` specifies the composition identities, ordered integration, coordinate limits and measured comparisons.

Each appearance change compares old/new Foreground and Background ink separately and marks only changed local cells in the corresponding Layer. Changing Background alone can alter contrast while leaving visible Foreground unchanged. Simple mode Display groups dirty cell runs into rectangles, expands them by one horizontal pixel for neighboring color dependencies and decodes its retained RGB cache; Presentation converts only these decoded regions into its retained RGBA picture before uploading the small native image. In CRT mode CrtDisplay takes the first and last dirty cell of each cell row, rounds their union outward to seven-pixel HGR fetches, and encodes that interval on the intersecting scanlines. The HGR encoder includes the following fetch for delayed serial-bit carry. The library compares only the returned sample interval and propagates electrical/optical damage; GPU decoding still processes complete changed rows. Initial loads, layer changes, effect changes and renderer switches use complete source lines. The sibling `crt/native` presenter owns either a direct GPU surface or SDL CPU fallback. GPU processing covers decoding through output encoding, with no ordinary frame readback; CPU fallback uploads only damaged CRT rectangles. Layer selection, scene reload and renderer switching refresh all source rows while retaining the CRT renderer. Window resize reconstructs existing light at the new drawable size without re-decoding. Dirty flags commit after successful native submission/presentation; pending surface retries retain their own redraw request. `sources/analysis/RENDERING.md` specifies the transaction and validation.

`CRT_BACKEND=auto` selects hardware Metal/Vulkan/Direct3D 12 where available and falls back to the regular CPU pipeline on initialization or runtime GPU failure. `cpu` forces fallback and `gpu` requires acceleration. The presenter drops GPU ownership before SDL claims the same window. Retained source signals permit CPU catch-up after deferred GPU submissions. Both simple and CRT output use the selected backend, and neither backend controls game pacing. The native adapter owns the narrow unsafe SDL surface-handle and texture-destruction operations; the game does not perform graphics interop itself.

The keyboard exposes observation and acknowledgement directly. Clearing availability retains the last code; delivery replaces the latch, including repeated delivery of the same code. In classic movement mode, releasing a host key does not stop movement; Space supplies a stop command. Commodore movement stores physical arrow holds separately from the keyboard latch. At a supported, non-digging gameplay boundary with no fresh or pending key, it selects the most recently pressed held arrow, or stops a retained movement command if none remain. Arrow auto-repeat neither changes hold priority nor supplies gameplay keys. Releases never replace pending digs or controls; held movement resumes after digging without waiting for OS repeat. A code delivered while falling or digging remains unobserved until the game polls it. Diagnostic trace inputs are fresh acknowledged codes, rather than host key events or repeated reads of an unchanged latch. Playable recordings normalize their effective contribution to Apple II commands; a necessary stop is represented by Space.

Speaker access toggles drive at a virtual cycle. PLAY_NOTE advances countdown runs between low-counter wraps and pitch reloads, retaining each edge without instruction interpretation. Its first pitch countdown uses duration; subsequent ones use pitch. Incoming low counter affects the first duration segment. Muting retains countdown duration but saves the original three-cycle speaker-access difference. Note buffers append one-based and play last-in-first-out. Overflow reports an error rather than corrupting neighboring memory.

Live audio integrates speaker drive over globally indexed sample windows, preserving fractional-cycle boundaries across batches. Pruning retains the last preceding edge so future samples start in the correct state. SDL output applies a DC-removing filter and gain. The game submits audio and graphics at gameplay boundaries and intermediate presentation checkpoints before sleeping. Host rendering, audio conversion, and file parsing do not add emulated cycles.

The display paints its initial scene before starting audio and resets the host pacing origin when session execution begins, excluding device and lazy GPU initialization from the live timeline. Audio starts without a prefixed silent buffer. During paced waits the SDL host pumps native events at most five milliseconds apart, retaining queued input until the next interval's normal poll. Transition tunes retain their complete modeled duration and atomic trace interval while the window remains responsive to the operating system.

Player execution
----------------

MOVE_PLAYER resets the gold-pickup collision exception. Continued digging bypasses gravity and keyboard polling. Otherwise it checks ladder and centered-rope support, then active and background support below. Falling erases the previous sprite, selects a facing-specific animation, nudges horizontal adjustment, advances vertical adjustment, and collects centered gold or transfers the active marker into the next row. Landing plays its note before keyboard observation. The note's incoming low counter is row 15 on the bottom support branch and column on other support paths.

A fresh code replaces both persistent command bytes; otherwise they persist. Vertical and dig commands precede horizontal fallback. Subcell adjustments range from 0 through 4, centered at 2. Crossing a boundary transfers the active player marker; the previous cell receives background terrain except background brick becomes active empty. Horizontal movement blocks brick, stone, and trap. Downward movement blocks brick and stone but permits trap. Nudging can collect gold at the centered position.

Sacrifice, end-game, and skip controls mark the player dead but return to the current movement dispatch. The retained command may still move or dig before the main loop observes death. The pause handler suspends that dispatch until its explicit resume boundary.

Collection removes background gold, erases its graphics, adds 250, appends six original notes, and suppresses shape-contact death for the remainder of that player call. Otherwise shape contact may kill the player. The trace attributes a collision partner only when logical contact establishes that partner; anonymous shape contact is represented by death without guessing a partner.

Digging requires a brick below the adjacent empty cell. Twelve calls update debris and brick graphics; the thirteenth completes the opening. Interruption restores the brick and erases debris. Completion does not move the player despite the original DROP_PLAYER_IN_HOLE label. It removes the active brick, retains background brick, clears both graphics images, and allocates the first free slot among 0 through 29 with timer 180. Per-cell generations identify later openings independently of reused timer slots.

Control handlers include sacrifice, current-level restart, skip level, mute, speed adjustment, keyboard mode, and pause. Return is ignored without replacing the persistent movement command. Joystick selection codes report an explicit unsupported-device error. The SDL mapping exposes normal keyboard controls; raw capture codes also exercise original control handlers. The extra-life code has no dedicated handler.

PgUp/PgDown use separate LevelNavigation requests, codes 0x82/0x83, intercepted before the gameplay latch. They work while playing, falling, digging, paused, or waiting and suppress key repeat. A valid request closes the iris, loads the adjacent board, and opens into ready without executing gameplay, terminal phases, tunes, or bonus scoring. Score and difficulty persist; lives_used resets to one and attempt increments. Requests clamp at configured list endpoints, retaining state and clocks. Each navigation request, including a bounded no-op, is a zero-time application input/checkpoint for diagnostic trace replay; playable capture omits bounded no-ops and their empty intervals; it contributes no model events or cycles. Runtime counts it as one input-addressing slot rather than dropping it as an automatic transition. MAME skips comparison for this checkpoint, enters its ordinary loader directly, and resumes gameplay observation afterward.

Navigation checks pass for initial/ready selection, first/last endpoint no-ops, falling and pause interruption, score/difficulty retention, life-used reset, and trace/recording replay. The external MAME fixture resumes gameplay after both navigation directions, including leaving pause with a restored stack. Formatting, Clippy, affected CLI/recording/transition tests, release build, and a headed required-GPU navigation run pass. Each iris leg uses thirty frames over 0.5 seconds, including startup; a complete navigation close/open consumes one second of presentation time and no gameplay cycles.

Guards, holes, and exits
-----------------------

The game stores a vector of concrete guards with validated identities 1 through 5. The scheduler advances a three-phase pattern selected by guard count plus difficulty, consumes bits least-significant first, and advances the round-robin guard identity for each set bit. Each selected guard completes its state/physics/route update before the next guard sees it. A dead player aborts further guard movement.

Gravity distinguishes empty/player cells, supporting guard occupants, and background terrain. The game uses `GuardMode::Roaming`, `Carrying`, `Trapped`, and `Resurrecting`, with nonzero countdowns for the latter three. Centered pickup removes background gold and seeds a drop countdown of resurrection column plus one. Dropping decrements that countdown only at movement boundaries and retries with one when the terrain is occupied. Entering a hole drops carried gold above if possible, otherwise removes it from the remaining total. Centering inside background brick starts the trap timer and awards 75.

Route selection first handles trapped escape, then a supported route on the player's row. Otherwise it considers down, up, left columns from the farthest limit inward, and right columns from the farthest inward. Only strictly better pseudo-distance changes the choice. Horizontal distance is relative to the guard. Candidate searches preserve the original left/right stale-row-pointer asymmetry. Bottom-row search stops at row 15 instead of reproducing an out-of-map zero-page pointer-table alias read; ordinary boards with a supporting bottom floor stop earlier.

Resurrection timers update before hole timers and guard movement. The resurrection column advances modulo 28 once per ordinary round. Hole timers scan slots 30 down to zero, decrement once, draw refill stages at 20 and 10, and close at zero. Closure kills a player in the hole with an environment-contact occurrence, handles gold loss, restores brick in the active map and both graphics pages, and buries the matching guard. Burial searches empty background starting at row 1 and the current resurrection column, centers the guard, and starts resurrection time 20. Stages occur at 19 and 10; expiration retries each round until active occupancy is empty, then restores the guard and appends four notes. No empty resurrection location is an error instead of an out-of-bounds scan.

Exit revealing visits hidden ladders in reverse allocation order. Empty background becomes ladder while active occupancy remains intact. Revealed entries leave the pending list; blocked background defers an entry. Once all are processed without blockage, the original gold counter becomes 0xff. GoldProgress uses Collecting, RevealPending and Revealed states. Conversion and decrement preserve the original byte-counter wrap behavior for unusually crowded custom boards; ordinary gameplay checks named states. Exit availability indicates completion eligibility, not necessarily visibility of every ladder. A centered player on row zero completes when gold count is zero or 0xff.

Rounds and session transitions
------------------------------

A gameplay round starts before MOVE_PLAYER. Its ordered operations are player update, sound/delay, exit revealing and completion check, resurrection timers, resurrection-column advancement, hole timers, sound/delay, and scheduled guards. Completion skips the latter operations. Death stops subsequent gameplay. A committed Died or LevelCleared snapshot ends the round before presentation and the zero-duration reload checkpoint change session counters or actor identity.

Death increments lives_used and holds the captured pose while playing the fixed original 24-note tune. Ctrl+A and Ctrl+R both request a current-board restart; Ctrl+R retains score and counts another life used. There is no game-over limit or extra-life control. Completion increments displayed level, resets lives_used to one, and keeps the old board visible while awarding fifteen animated increments of 100 points with three notes each. The measured completion sequence lasts 898,922 microseconds; the measured death sequence lasts 440,313 microseconds. Both use fixed note onset schedules, independent of gameplay event-model timing and speed preferences. Pending gameplay notes are cleared before either tune. End-of-list wrapping increases difficulty; skip-level changes the selected board and resets lives_used.

Startup opens the board with a half-second circular iris. After either death or completion, the old board closes over half a second, board preparation runs immediately without simulated time, and the new board opens over half a second. The radius changes linearly, centered at native pixel (140, 88), and covers only the 280 by 176 playfield; status remains visible. Presentation applies iris masks and player hiding to scene copies so gameplay contact ink never changes. The ready player alternates visible/hidden every one-third second. A fresh non-repeat key starts play and enters the gameplay keyboard latch in that same step. Movement, digging, and controls act immediately when supported; falling or digging defers observation normally. The key is traced and recorded when gameplay observes it. Animation keys are drained before ready starts. Pause remains an in-level 5,000-cycle poll and Escape resumes it. Full transition behavior and one-time measurement provenance are specified in sources/analysis/TRANSITIONS.md.

No high score table exists in configuration, game state, snapshots, or changes. Live play and playback ignore existing highscores.json and never create or update it. Native play never enters game over.

Observation and trace replay
----------------------------

The observer consumes committed snapshots and a transient occurrence journal; it does not simulate gameplay rules. Snapshots contain session level/attempt/phase/score/lives_used/exit availability, actor cell/subcell/facing/motion/action/lifecycle/carried gold, both terrain maps, pending ladders, and holes with generations. Scheduler internals, delay preferences, animation bytes, and countdown values remain execution state. Gold identity is a location or carrier, not an invented permanent identifier.

The sole cycle-based record is interval start as a delta from the previous start. Events inside are untimed. Empty intervals remain for input addressing. A final delta closes the last interval. Net snapshot changes are atomic and canonical by identity. Occurrences are not reapplied as mutations. Episodes preserve order per subject; independent subjects sort canonically. Consecutive contact runs sort and deduplicate, while non-contact occurrences retain their order. Observed inputs retain order and observation ordinal; this port supports at most one keyboard observation, ordinal zero, per interval.

Trace format version 4 carries reference/configuration identity, initial gameplay snapshot, rounds, final duration, and final snapshot. The session counter is lives_used: u32. Version 3 traces are unsupported. Startup and idle ready waits produce no trace intervals, elapsed gameplay time, or inputs. The starting key enters the first gameplay interval and is recorded at its normal observation boundary. An instantaneous board checkpoint records final bonus/reload state between terminal gameplay and the next board, without intermediate score updates, notes, iris frames, or waiting. These checkpoints have zero gameplay duration and are excluded from MAME comparison. Ready snapshots normalize phase to Playing, and replay dismisses ready automatically. Parsing checks domains, identities, ordering, clock overflow, change preconditions, and terminal state.

Replay constructs a fresh Run from embedded configuration and compares initial identity/state. For each expected interval it injects only its observed key through the keyboard device, executes the appropriate phase, and compares the independently generated round exactly. Expected changes and occurrences never drive execution. It also compares final state and duration, rejecting the first mismatch. Delayed keyboard deliveries can be injected at their observation interval because they had no prior observable effect. Unobserved host events are intentionally absent. Same-implementation comparison has zero tolerance; later emulator cross-validation may introduce interval timing tolerance without accepting gameplay differences.

Ordinary play and input recording disable trace history before execution. `Run::last_inputs` exposes keys consumed by the newest committed interval regardless of tracing. Tracing and validation retain canonical rounds for external comparison. `--input ROUND:HEX` schedules deliveries for development through the same session path.

Startup, recording, and verification
------------------------------------

`cli::Arguments::parse` selects Live, Recording or Trace playback and resolves display, pacing, bounds, renderer and validation options. `--renderer crt` is the default; `--renderer simple` selects digital artifact output. A grouped keyboard summary prints at startup and appears in --help. The SDL window is resizable and high-DPI aware. Developer modes start at 1120×768 (4×280×192); ordinary play restores its saved fitted size. Ctrl+=/Ctrl+- snap native scale and C switches rendering modes; these commands remain available during playback and never reach the gameplay keyboard or recordings. Auto-repeat is ignored for window actions. Both modes fit a centered 280:192 picture within arbitrary drawable dimensions with black letterboxing. Snap keys use window-coordinate dimensions, while CRT reconstruction uses physical drawable pixels. No arguments starts displayed live play; `--replay FILE` defaults to display; `--verify FILE` defaults to headless. `--headless` and `--display` are exclusive. Headless live execution requires a positive `--rounds`; playback uses its stored endpoint, optionally shortened by `--rounds`. Playback rejects level or scheduled-input overrides. Input schedules reject duplicate or out-of-range intervals and codes without the high bit. MAME options require a validation workflow. `--trace FILE` and `--verify FILE` imply MAME validation; `--validate` enables it without a trace destination. `--record FILE` can accompany any mode with a separate path.

`runtime::Session::new` resolves input/output paths before execution, rejecting matching paths and symlink aliases. It loads live configuration from original level assets, or restores configuration from playback. `Run::new` validates and decodes the configured boards before SDL opens. Playback never consults or updates filesystem scores. A host polls once per interval and supplies a quit flag plus a possible key. Session chooses a recorded, trace, scheduled or live delivery, advances Run with the host presentation callback, and captures effective gameplay commands. Diagnostic traces independently retain all consumed inputs. SDL submits sound and graphics before Run paces; headless execution submits neither and prunes unused speaker history.

Recording JSON version 2 contains configuration, total gameplay rounds, and a sparse map from zero-based gameplay interval to effective high-bit Apple II command. Configuration embeds level sectors, starting board, and wait policy. Startup, transition intervals, and idle ready polls are absent; unlike traces, recordings need no board checkpoint. Playback infers transitions from terminal gameplay, runs the presentation sequence, dismisses ready automatically, then injects the next recorded gameplay key. Silent gameplay intervals need no map entries, and endpoints preserve trailing gameplay silence. Live capture suppresses sound/speed controls, Return, duplicate directions and ineffective actions. It tracks the persistent movement command implied by playback, records successful movement or dig commands only when needed, and emits Space when that retained direction would otherwise move. A failed direction or dig can therefore contribute a stop without retaining the rejected key. Initially blocked movement is recorded at its first effective boundary; if a death/skip control also executes it there, capture retains its prerequisite at the earlier command observation. Pause/resume and effective level navigation remain recorded. Bounded navigation no-ops consume no recording interval. Importing existing recordings preserves their codes verbatim. Gameplay snapshots are reproduced, while audio preferences and modeled cycle timings can differ from live play. Parsing rejects missing/unknown fields, unsupported versions, out-of-range keys, and invalid codes. Version 1 recordings are unsupported.

Normal interactive play uses an installed SQLite catalog and a separate player database. Explicit `--record`, `--replay`, `--trace`, `--verify`, validation, bounded runs, and scheduled-input runs remain isolated development workflows with embedded original boards. They do not open player databases or update application preferences. Input recording format 2 remains configuration, effective commands and endpoint only; there are no guard delay, resurrection, or timing overrides. Developer traces retain format 4 and their independent machine-validation workflow.


Application data and installation
---------------------------------

`make` incrementally builds `target/levels.sqlite3` from `sources/levels/{classic,professional,revenge,fan-book,championship}.js`, `sources/build_catalog.py`, and the catalog/recording SQL schemas. The five data files are copied from Total Recall revision `cceca5d5a15a21f724836654a46bf2501968e142`; original source comments preserve their board provenance. Python reads the data-only quoted-row arrays, validates board lengths, tile characters, player presence and expected pack counts, populates a temporary database in a transaction, checks foreign keys, closes it, and atomically replaces the build output. There are 434 levels: Classic 150, Professional 150, Revenge 17, Fan Book 66, Championship 51. No Total Recall recordings are imported. Total Recall's separate UTF-16LE wData.js contains a full solution collection, but it is not used by this application.

Only `make install` copies the current release executable to `~/.local/bin/loderunner` and the catalog to `$XDG_DATA_HOME/loderunner/levels.sqlite3` (default `~/.local/share/loderunner/levels.sqlite3`). BINDIR and DATADIR override these installation paths; DESTDIR stages them. Building or launching never installs a catalog. Normal startup resolves paths independently of the executable location and working directory. It searches the user's XDG data directory first, then absolute XDG_DATA_DIRS entries (default `/usr/local/share:/usr/share`) for the read-only catalog. Missing catalogs produce an installation diagnostic. Player data always stays under the user's XDG data directory, even when the catalog is system-wide. Relative XDG values are ignored. SQLite is bundled through rusqlite, with synchronous connections and explicit write transactions.

The catalog normalizes `level_packs(pack_name, pack_order)`, `levels(pack_name, level_number)`, `tile_kinds(tile_kind, symbol, description)`, and `level_tiles(pack_name, level_number, tile_row, tile_column, tile_kind)`. Pack name, one-based level number and cell coordinates are natural primary keys; all tables use WITHOUT ROWID. Catalog lookup checks contiguous cell/level ordering and decodes every board before opening SDL. Runtime packs retain their source names and menu order. Natural joins on shared names link packs, levels, cells, and tile kinds.

The native five-guard allocation limit still applies. Classic levels 8, 80, and 113 and Championship level 35 each contain six source guard markers; initialization retains the five selected by the existing reverse traversal. All markers remain represented in catalog tile data. Vendored source attribution is recorded in `sources/levels/provenance.json`; trailing source whitespace is normalized without changing board strings.

The catalog and player database both contain `recordings` and `recording_inputs`. The installation recording tables start empty and reserve supplied-solution storage for future native recordings. `recordings` is keyed by `(pack_name, level_number, started_at)`; timestamps are UTC Unix microseconds. It stores process-session start time, outcome (`win`, `death`, `restart`, `abandoned`, `quit`), active gameplay cycles, interval count, player gold collected, guard burials, and typed JSON initial state. `recording_inputs` uses that natural identity plus zero-based round_number, stores acknowledged high-bit codes, and cascades on recording deletion. These tables use WITHOUT ROWID. Player pack/level references intentionally have no cross-database foreign key and survive catalog rebuilds. The player database uses WAL and a five-second busy timeout. Both schemas use user_version 1; unsupported versions fail clearly.


Attempt recording and retention
-------------------------------

Each normal player attempt begins immediately before the first active input/step on a fresh board. Ready waiting is excluded. Its initial-state seed includes score, lives used, attempt counter, difficulty, resurrection column, guard scheduler phase and facing history, player facing, pending falling sound/pitch, mute and speed. Board reload preserves some of these values, so storing keys alone would not make later attempts independent. Playback validates the seed, rebuilds the board's initial composition from the catalog, restores the seed and scheduler, and executes recorded Apple II commands. It never applies expected trace state. Developer format-2 file recordings remain separate from this database representation.

Run exposes a transient occurrence journal even when trace history is disabled. Each committed player interval captures its effective command, counts player gold-collection and guard-burial occurrences, and accumulates modeled cycles for active gameplay, excluding paused polls. Terminal death/completion closes the attempt before presentation and bonuses. Ctrl+R closes the attempt as restart and immediately invokes terminal presentation even when paused, falling or digging; valid level/pack navigation records abandonment; normal quit records quit. Bounded endpoint navigation leaves an ongoing attempt intact. Automatic reload creates the next attempt only when play begins. Idle waits and demonstration playback never create player attempts. Unfinished attempts are held in memory and are finalized on ordinary exits, including handled execution errors; abrupt process termination cannot recover that unfinished prefix.

Header insertion, input insertion and per-level pruning commit atomically. If the timestamp collides or the wall clock moves backward relative to an existing recording for that level, insertion advances it to the latest stored timestamp plus one microsecond. Pruning permanently protects the fastest win (newest breaks ties) and the newest win. Other wins and useful failures remain for thirty days; the best useful run per process session can remain for ninety days. Session ranking prefers wins, then more player gold, longer gameplay, and recency. Failed attempts shorter than one third of the best local winning duration are discarded; before a local win exists, the minimum useful failure is ten modeled seconds. An ordinary short attempt can therefore be recorded and removed by the same transaction. Cascading deletion removes its inputs. Supplied-solution tables are currently empty, so no external winning baseline is used.


Recording synchronization
-------------------------

Before merging recordings, synchronization compares each host's maximum recording `started_at`. Only a strictly newer host supplies the selected pack, complete per-pack remembered-level map, playing `frame_period`, and `demo_frame_period` to the other host. An empty recording collection loses to a nonempty collection; equal timestamps and two empty collections leave preferences unchanged. The settings come from each host's configuration snapshot, not the recording's initial state. Missing configuration uses the application's defaults (Classic, level one through an empty map, and both periods six), including the legacy demo-speed migration to period six. Other destination preferences are preserved. Configuration writes use atomic replacement after successful recording imports; database commits and configuration replacement are separate operations, so a later configuration failure does not undo imported recordings. Each host resolves XDG_CONFIG_HOME independently with ~/.config as fallback; --local-config and --remote-config override config.json paths. The sync tests use isolated database and configuration paths.

`sync-recordings.py TARGET` merges the two player databases through a single SSH connection. Python 3.10+ and its standard-library SQLite module are required on each machine; only the initiating machine needs the script and SSH client. The local script sends its own source as a quoted `python3 -c` command, leaving stdin/stdout for newline-delimited JSON requests and replies. SSH stderr carries authentication and remote errors. Each side resolves its own absolute XDG_DATA_HOME or falls back to ~/.local/share; --local-db and --remote-db override player paths, with remote tilde expansion performed by Python. Missing databases and user_version other than 1 fail rather than creating or migrating databases.

Both sides begin SQLite read transactions and exchange recording headers. Pack, level and UTC start microseconds form the identity. Shared identities must match all other header values, including parsed initial-state JSON; input rows are deliberately not compared. Conflicts stop before imports. The local side retains inputs for its local-only headers from its snapshot, then requests remote-only headers and inputs from the remote snapshot. Each side releases its read transaction after exporting, so later writes use fresh transactions. Snapshot retention keeps headers and inputs coherent even if gameplay concurrently prunes a recording.

The local side imports the remote bundle under BEGIN IMMEDIATE with foreign keys enabled and a five-second busy timeout. Headers and sparse input rows commit together; invalid inputs or conflicting concurrent inserts roll back that direction's entire batch. An identity inserted concurrently is skipped only if its metadata matches. After reporting the local committed count, the local side sends its outgoing bundle for the equivalent remote transaction and waits for the remote committed count and successful SSH exit. A failed second phase preserves the first commit; rerunning completes remaining transfers without duplicating recordings. A lost acknowledgement can leave the remote commit successful but unconfirmed, also resolved by rerunning. Recordings finalized after the snapshots wait for the next sync.

Sync never updates timestamps, preferences, catalogs or retention, and never propagates deletions. Normal game saves still prune their affected level; syncing can restore recordings still retained on the other machine. Timing and fidelity limits
--------------------------

Virtual cycles come from the calibrated event model and do not depend on host execution speed. Host sleeps target absolute deadlines at nominal NTSC 1,023,000 Hz, once per completed interval. Headless execution does not sleep. `sources/analysis/TIMING.md` and `EVENT_TIMING.md` retain the original timing analysis and calibration evidence.

The original attract/demo mode, level editor, joystick devices, and spinning game-over presentation are outside this keyboard gameplay milestone. Iris geometry is reproduced with a fixed linear radius schedule rather than original machine timing. RGB artifacts and host speaker filtering remain approximations. Sound-buffer overflow and impossible resurrection boards fail cleanly.

Event-timed port execution
-------------------------

The root `loderunner` library and executable use concrete `Board`, `Player`, `Guard`, `Position`, `Holes`, `Sound`, `Score`, `Scene`, and `Display` types. Gameplay and graphics functions never advance time or compute costs. Only application presentation can advance the separate presentation clock; Display has no pending-cycle accumulator, and TimingInterval contains only starting/ending phase and events.

`GuardSchedule` stores three-phase update counts, not bit masks. Each selected update advances the rotating guard cursor; player death stops the remaining updates. The phase survives reloads while the cursor restarts.

`Board` stores the fixed 28-by-16 terrain and current cell contents. `Position` holds a cell plus two private alignments in the range zero through four, centered at two. Traveling across an alignment edge changes cells and restarts at the opposite edge; perpendicular centering moves one alignment toward two. Leaving an actor cell restores terrain except a dug brick becomes empty. Player and guard movement share this geometry but keep separate obstacle, collection and animation rules. PlayerFrame and GuardFrame name each animation frame and retain separate movement sequences. Their validated `Sprite` identities are used by appearance operations and the timing model. Named terrain, refill, resurrection and glyph sprites keep numeric asset identities at the appearance boundary. `paint_cell`, `overlay_cell` and `erase_cell` convert board cells to reference coordinates; actor placement retains the uneven alignment geometry. Position::half_x_and_pixel_y explicitly returns horizontal half-pixels and vertical pixels. Shared asset decoding is separate from whole-shape appearance updates and RGB presentation.

`Game::play_round` updates the player, sound, exit state, timers, holes, and scheduled guards in original order, stopping at committed death/completion. `Run::step_with_checkpoint` records terminal/input work and commits the model only for in-level intervals. Terminal phases dispatch application presentation through intermediate checkpoints while gameplay time stays fixed; their final reload is one zero-duration board checkpoint. Waiting polls are presentation-only and produce no committed timing record or consumed gameplay inputs. Capture and replay share this Run path.

The player owns its alive flag, collected-gold exception, persistent `Command`, and optional `Digging`. A supported update lands and observes input before dispatching `Stop`, `Move(Direction)`, or `Dig(DigSide)`. Gravity and continued digging bypass observation. Named Control values decode raw input codes at the keyboard boundary. Controls retain the prior command unless a normal command key replaces it; sacrifice still executes that command, while pause suspends it. Movement runs eligibility, erase, perpendicular centering, travel, collection and animation/draw once for all four directions. The original command and horizontal-fallback bytes receive the same values on supported keyboard paths, so one command preserves their behavior.

`Digging` uses one validated chronological stage from zero through twelve for either side. Twelve updates draw directional debris and progressive brick sprites; the thirteenth queues its final note, redraws the player and opens the hole without moving the actor. Starting a dig clears the persistent command. Missing brick cancels without restoration; an occupied adjacent cell restores the brick and erases the previous debris, if any. Gold checks during horizontal/vertical centering retain their execution order.

Guard mode determines whether an update waits, shakes, attempts escape, falls, or chooses a route. A trapped update decrements its release countdown; values at least thirteen wait and values seven through twelve shake. Values one through six attempt movement without gravity. Expiring the countdown returns to roaming; a blocked upward escape extends a still-positive countdown. Resurrection is a separate mode that suppresses scheduled movement while round-based timer updates draw its appearance stages. Route selection is an immutable board query in `routing.rs`. It returns an optional direction and whole-search extents. Typed ranks prefer the player row, then rows above, then rows below; distance breaks ties within each class and equal ranks keep the first candidate. Search order is current column down/up, left columns from the far edge, then right columns from the far edge. A non-rope left neighbor shifts the downward search’s right rope test down one row; at column zero that shift does not happen. Movement checks obstacles separately from same-row pursuit.

`Holes` contains thirty optional records in allocation order, each carrying its cell, nonzero remaining lifetime and generation. It allocates the first free entry and refills in reverse order. Generation counters are per cell and increment only on successful timer allocation. An opening made while all timers are occupied remains untracked, matching original behavior. `Sound` is a last-in-first-out stack of complete notes capped at 127; `append_notes` fails atomically on overflow. Playback uses the stack length before popping as the note's incoming low counter. `Score` uses decimal points directly, wraps at eight digits and draws the same seven sprite digits.

Reloads replace board-local state in place, resetting actor positions, animation, commands and dig state while retaining player facing, guard scheduler phase and a five-identity facing history in Game. The history includes identities absent from the current board, so a smaller guard roster does not erase direction needed by a later larger roster. New-game restarts retain this history too. Existing falling-sound, score/life/session and timing-journal preservation rules apply unchanged.

At interval entry, Run records the start cycle and clears the Clock work collector. Clock owns both event counts and pending draws; Display owns only presentation state. Counts describe executed gameplay work. Ordered `Work` records describe draws (`DrawKind`, sprite and position), notes (enabled, pitch, duration and incoming low counter), and sound-section boundaries (buffered duration/period, falling, or idle period). Appearance helpers retain original rendering inputs rather than deriving a duration; native dirty-region decoding and SDL uploads add no model events. `play_note` records a note without touching the speaker. `play_sound_section` flushes pending graphics work, records its beginning, applies note-stack/falling-pitch state changes, records the note if any, and records its ending. Landing notes precede subsequent player graphics. Final graphics work flushes at interval completion.

The model reads per-sprite setup costs generated at build time and computes placement costs with whole-sprite arithmetic, including the vertical lookup boundaries and seven-pixel alignment. No runtime sprite-plane or scanline-cost loop remains. It evaluates the fixed graphics and sound terms once per interval and adds calibrated event corrections. Reference note synthesis lives in `sound.rs`; it preserves the audible counter behavior without dictating gameplay control flow. Its only duration path is the sum of terms, rounded once and bounded below by zero and the sound work's duration. No phase reads a legacy cost. Poll events carry the configured 5,000-cycle batch coefficient. Pause-entry events carry a correction calibrated against a 187-cycle MAME control fixture: the correction plus the ordinary Round/Input terms equals that measured duration. GraphicsCycles and SoundCycles are internal model features, never measured journal entries.

The native model uses eighteen whole-operation features plus fixed graphics/sound terms, with no branch probes, candidate-improvement counts, or distance-class counters. `fit_port_model.py` fits training levels and chooses regularization on validation levels; test levels only report results. `port-model-report.json` records the measurement digest and errors. Held-out RMSE is 444 cycles versus 342 for the branch-heavy model and 1,699 for procedural timing; worst held-out error is 1,390 cycles (2.775%). This precision/simplicity trade-off remains within the machine-validation allowance. Captures require the same coefficients for exact replay; older captures may no longer replay under the native model.

Model audio placement follows ordered work. It preserves each note's countdown durations, speaker toggles, muting behavior and low-counter/pitch-zero wrapping. The total non-sound duration is distributed in proportion to the fixed draw-work costs; when no draws exist, it precedes the sound work. Sound-section prefixes/tails retain their fixed sound terms. This applies the fitted timing correction to gaps without changing note pitch. Every edge lies within the committed interval, and speaker drive persists across intervals and reloads. Individual speaker timestamps across a complete mixed gameplay turn follow the fitted event model.

At the end of a successful gameplay interval, Clock renders its speaker work and advances gameplay cycles by the event model result. Speaker timestamps and SDL deadlines use output_cycles, the sum of gameplay cycles and presentation-only cycles. Transition tunes, iris frames, and ready polls advance presentation only. Audio uses one continuous sample index across both domains. Gameplay time remains stationary during these sequences, so no transition duration enters tracing or model calibration. Each presentation checkpoint submits small audio batches and the current picture before pacing. Native events are pumped in waits at most five milliseconds apart.

Initial board rendering and every reload run at host speed outside gameplay time. Loading resets board cells, actor poses, holes, ladders, keyboard availability, queued notes, and presentation caches; it preserves facing history, scheduler phase, falling sound, preferences, and accumulated score. Initialization paints the retained status values. Transition draw journals are discarded rather than passed to the gameplay event model. Score has one authoritative Game value and is copied into observations only at gameplay boundaries.

Capture, live play, input playback, and trace verification share committed gameplay model time and the separate presentation offset. There is no gameplay timing selector. Exact native replay compares gameplay rounds, board checkpoints, and terminal gameplay state/duration. Trace version 4 and input-recording version 2 exclude startup and idle ready waits and reject older formats. Starting commands are recorded through ordinary gameplay observation. Historical comparisons established logical and pixel equality across selected older implementations; current portable and external gameplay checks remain the authority for changed behavior.

MAME trace validation workflow
-------------------------------

Every validation mode starts a worker from the game's initial trace. Each committed interval publishes its canonical round, closing duration and snapshot through a channel whose send never waits for MAME. Queued intervals remain in memory until consumed, so validation lag does not alter game pacing or audio submission. Validation uses one MAME process and the same comparison path as offline library validation. Idle time awaiting intervals does not consume the machine-operation deadline. A disconnected channel drains accepted work before stopping MAME. A mismatch saves the stopped machine and closes the receiver; the game stops at its next boundary. The application saves completed trace/recording prefixes and joins the worker before reporting failure. All CLI MAME options apply to this worker. The executable defaults to `mame` on PATH. Packaged plugin modules are discovered from the resolved executable installation; `--pluginspath` overrides that path. Explicit relative executable, ROM and plugin paths resolve from the caller's directory before the child enters its isolated work directory. External Make checks accept MAME and ROMPATH installation overrides.

`src/mame/` accepts a structurally valid version-3 trace with the pinned reference source identity. Configuration contains one through 150 complete 256-byte sectors, a valid starting index, and a ready-screen wait policy. Each interval supports at most one observed high-bit key at ordinal zero. Unsupported identities, configuration or input shapes fail before executing gameplay. The library exposes `validate` for complete traces and `validate_stream` for interval producers; the root application owns startup and input playback.

The validator creates an empty, isolated work directory and extracts the playable disk from the tracked 4am archive, verifying its SHA-256. It replaces all configured level sectors and clears remaining level sectors, so the original loader detects the configured list's end through its own invalid-board path. It leaves the original score sector untouched; score routines are bypassed by the boundary adapter. The source archive is never modified. MAME's configuration, NVRAM, disk diffs, and saves use private directories within this work directory.

Firmware reset and floppy loading execute normally on enhanced IIe with W65C02. The adapter's first conditional breakpoint identifies application entry at $6000. It delivers splash Space through the keyboard device. At INIT_GAME_DATA, it sets configured displayed level and disk index and applies the approved `fixed-v2` initialization once: player-facing $05, guard-facing $0C91 through $0C95, and guard scheduler phase $64 become zero; falling-pitch counter $A4 and landing-sound flag $9B become $20. A nonzero $9B means no pending landing sound, corresponding to native initial false state. These values eliminate loader residue and are not reapplied after death, completion, or new game. The optional original-initialization mode leaves residue intact and is expected to expose incompatible initial state when it matters.

The initial snapshot occurs at ready cursor $8700 when waiting is configured, or at main-loop entry $60E4 after automatic keyboard-mode Ctrl+K otherwise. Startup input observations and source-path signals are discarded before this initial gameplay snapshot. After later loading, the adapter either samples Waiting or automatically supplies Ctrl+K to bypass the ready cursor according to the same configuration. Automatic setup inputs are not recorded as user inputs. Expected initial state is compared exactly before the first trace input is delivered.

Gameplay intervals finish at the next $60E4 entry, death $613F before decrementing lives, or completion $611A before awarding score. Pause entry is sampled before waiting for another Escape, and resumption before jumping back to CHECK_FOR_INPUT. Return-menu and score-recording entries redirect the program counter to the existing RTS at RECORD_HI_SCORE_DATA_TO_DISK.end. This explicitly adapts behavior outside the core fidelity boundary without executing menu or score logic. Game over is sampled at spinning-animation entry. A new INIT_GAME_DATA resets attempt identity and observer history, including when the previous attempt was already zero.

LOAD_LEVEL increments attempt once per death/completion reload, including an invalid-board retry that wraps the disk index. New-game initialization restores the configured starting index and attempt zero. Positions, maps, and flags in every resulting sample come from MAME RAM; the adapter does not assign expected actor coordinates, tiles, scores, timers, or branch outcomes. Phase labels and interval boundaries follow executed original source paths. Non-gameplay empty polling intervals stop at a keyboard-poll instruction after at least 5,000 CPU cycles. A pending key must be observed and processed before an input-bearing interval can close. Poll thresholds use hexadecimal debugger expressions; they are CPU-cycle thresholds, not host timers.

Every stopped sample includes relative CPU cycles, independently determined phase/attempt, mapped $0000-$1FFF RAM, observed inputs, and source-path signals. C000 reads return the adapter's latch; either read or write at C010 clears its high bit while retaining its code. The first high-bit read of a delivered key records it once; multiple original reads before acknowledgement do not duplicate that observation. The validator injects only the expected interval's key. Expected changes and occurrences are never sent as execution commands or used to advance game state.

Most trace state is decoded from persistent RAM: active/background maps, player coordinates and flags, guard parallel arrays, hole coordinates/timers, pending ladder arrays, score and level. The application life-used counter is derived from board and reload identities. Hole timer thresholds map to Open, ClosingFirst, and ClosingSecond at greater than 20, 11 through 20, and 1 through 10. Hole generation increases when a cell reopens after disappearing from an earlier snapshot and resets with attempt/new-game identity. Named motions cannot be derived reliably from final coordinates alone, so source-path signals record selected guard, supported input dispatch, successful directional movement, and gravity. These signals maintain observer motion history without simulating routes or movement rules.

Narrow instruction anchors preserve occurrences that snapshots could miss: collection, dropping gold, landing, trapping, actor contact, and closing-hole contact. Breakpoint actions record these observations synchronously and continue execution. The shared decoder produces object subjects and occurrence journals; the canonical observer emits net changes and sorts/deduplicates contact runs under the same contract as native capture. A collision is attributed to a guard or environment cell only when the corresponding original path establishes that partner. Framebuffer death without that evidence is not assigned an invented object.

Breakpoint addresses come from `sources/analysis/apple2-symbols.json`, regenerated from the pinned assembly and assembled image. The generator handles original includes and data directives and advances instruction lengths using legal NMOS opcodes; it does not execute instructions. Unnamed occurrence anchors are unique binary patterns in bounded source regions. Ambiguous anchors fail setup. The 4am gameplay compatibility audit establishes why these source addresses apply to the external disk.

The headless debugger automatically resumes after its callback returns. Therefore sample publication and command consumption happen within the stopped callback: an atomic sample file appears, the adapter waits for the matching atomic command file, then continues or saves/exits. Repeated cycle reads around sampling assert that observer work charges no CPU time. Input-only commands contain a key and stop/save flags. The host has a bounded timeout, kills/reaps an unfinished child on error, and retains artifacts for investigation. No process remains running after validation returns.

Each fresh decoded sample enters the same canonical Observer as native capture. Logical rounds compare exact input observations, changes, and occurrence episodes; only the start delta is removed from this exact logical comparison. The current interval's expected duration is the next round's start delta or the trace's final delta. Actual duration is the difference between consecutive MAME sample cycles. Boot/setup and the first round's absolute origin offset are outside duration comparison. Consequently one timing drift does not invalidate subsequent intervals, and the last interval cannot evade timing validation.

All validated in-level intervals, including terminal gameplay ending in Died or LevelCleared, use the gameplay allowance of 2,000 cycles plus 10 percent by default. Transition checkpoints are excluded from both state/event comparison and timing reports. Startup/loading/iris/ready cycles and synthetic ready keys are subtracted in the MAME adapter, and remaining lives are replenished outside gameplay to permit unlimited reloads. The independent machine observer derives lives_used from sampled board identity and reload identity. Arithmetic uses a wide accumulator. Successful reports record MAME version, initialization profile, gameplay allowance, per-gameplay timing, and work path.

The first mismatch writes expected/actual difference data, immediately saves the stopped MAME machine as `failure.sta`, and records PC, cycles, phase, attempt, latch and latch-observation status in `checkpoint.json`. The custom latch is external to MAME's save-state serialization. Raw samples, input commands, the submitted trace, prepared disk, and full process output remain available.
